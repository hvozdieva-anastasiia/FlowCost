# Flow Cost: итог исследования идеи плагина

Дата: 2026-11-13. Статус: идея выбрана пользователем, проект не начат. Этот плагин не связан с Personal Notes & Tasks: отдельный продукт, отдельная рабочая папка и отдельный plugin ID.

## Решение

Следующим плагином делаем **Flow Cost**: калькулятор «стоимости» пользовательского сценария по готовому прототипу Figma. Только фронтенд (React в окне плагина, логика в Plugin Main), без бэкенда, ИИ и аккаунтов.

Критерий отбора на этом этапе ослаблен по решению пользователя: не «нет ни одного плагина вообще», а «нет сильного конкурента в этой функции». Flow Cost при этом проходит и строгую версию: в каталоге нет плагина с такой функцией.

## Боль

- Команды вручную перечисляют шаги и «точки трения» в старом и новом сценарии, чтобы показать разницу. Пример: Lucid посчитали 19 точек трения против 26 (минус 26,92 %) ([статья](https://medium.com/lucid-software-design/how-to-quantify-and-reduce-friction-in-user-experiences-e30b1a332074)).
- UX-дизайнер применяет KLM к кликабельному прототипу, чтобы сравнить варианты до юзабилити-теста ([статья](https://medium.com/enterprise-ux/key-stroke-level-model-213dd054e5c7)).
- Дизайнерам нужно обосновывать упрощение потока перед заказчиками числами ([UserTesting](https://www.usertesting.com/blog/ux-design-metrics-performance-efficiency)).

Слабое место доказательств: жалоб на форуме Figma с просьбой считать шаги по прототипу я не нашёл. Доказательство есть только как практика команд. Клики и шаги сами по себе слабая метрика ([Indeed](https://medium.com/indeed-design/breaking-the-myth-of-big-click-energy)), поэтому плагин подаём как быструю оценку до теста, а не замену тестам с людьми.

## Проверка конкурентов

Каталог Figma Community, запросы: KLM, GOMS, Hick's law, task time, interaction cost, click count, user flow steps, prototype metrics, prototype flow analysis. Подходящих плагинов нет. Ближайшие:

| Плагин                                        | Чем отличается                                                                                      |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Prototype Flow Auditor                        | Проверяет только структуру: нет старта, недостижимые экраны, тупики. Не считает шаги, время, усилие |
| Prototype Preflight                           | Аналогично: проверка графа перед тестом                                                             |
| TapTail, Pathway, Wynde, UserTesting          | Поведение реальных людей, нужен сервер и сессии                                                     |
| Klever, Versive, Velocity и другие ИИ-тестеры | Недетерминированные оценки ИИ                                                                       |

Оговорка: поиск каталога периодически упирался в лимит запросов и возвращал пустой результат. Пустые ответы я не считал доказательством. Перед стартом разработки стоит повторить запросы вручную в каталоге.

## Что делает плагин (черновик)

1. Читает прототипные связи страницы: реакции узлов (`reactions`), точки входа потоков (`PageNode.flowStartingPoints`).
2. Пользователь выбирает начальный и целевой экран (или поток).
3. Считает:
   - число шагов и экранов в кратчайшем пути и в альтернативных;
   - оценку времени по KLM (нажатие, указание, мысленный шаг, набор текста), с временем указания по закону Фиттса из размера и расстояния зон нажатия;
   - «точки трения»: оверлеи, прокрутки, поля ввода, ожидания по таймеру.
4. Сравнивает две версии сценария («было / стало») с разницей в процентах.
5. Экспортирует результат в Markdown и CSV.

Константы KLM берутся из литературы и доступны для правки пользователю.

## Подтверждённые возможности Plugin API

- Типы действий: `NODE` (с `navigation`: `NAVIGATE`, `OVERLAY`, `SWAP`, `SCROLL_TO`, `CHANGE_TO`, и `destinationId`), `BACK`, `CLOSE`, `URL`, `SET_VARIABLE`, `SET_VARIABLE_MODE`, `CONDITIONAL`, `UPDATE_MEDIA_RUNTIME` ([Action](https://developers.figma.com/docs/plugins/api/Action/)).
- Триггеры: `ON_CLICK`, `ON_HOVER`, `ON_PRESS`, `ON_DRAG`, `AFTER_TIMEOUT` (с `timeout`), `MOUSE_*` (с `delay`), `ON_KEY_DOWN`, `ON_MEDIA_*` ([Trigger](https://developers.figma.com/docs/plugins/api/Trigger/)).
- `PageNode.flowStartingPoints`: упорядоченный список точек входа потоков ([PageNode](https://developers.figma.com/docs/plugins/api/PageNode/)).

## Риски и открытые решения

- Прототип должен быть связан. Условная логика на переменных (`CONDITIONAL`, `SET_VARIABLE`) усложняет расчёт пути: для первой версии нужно решить, считаем ли ветки или помечаем экран как «не рассчитано».
- Оверлеи, `BACK`, `SWAP`, `CHANGE_TO`: правила учёта шагов нужно зафиксировать до реализации.
- Определение поля ввода только по эвристикам (тип компонента, имя слоя). Нужна ручная правка.
- Время набора текста зависит от длины текста: брать из шаблона или спрашивать у пользователя.
- Единицы и допущения (эксперт или новичок, десктоп или мобильное устройство) влияют на KLM: нужен выбор профиля.
- Интерфейс только на английском, как в Personal Notes & Tasks, если пользователь не решит иначе: открытый вопрос.
